# Runtime design

`app.py` creates Flask instances and registers the web and execution blueprints. Importing it does not create databases or launch workers. `config.py` is the shared configuration boundary for both processes; `context.py` creates an application-scoped repository lazily. `tool_base.py` holds the plan contract and shared validation; `adapters.py` owns the registry, `disk_tools.py` and `examination_tools.py` implement their tool families, and `tool_results.py` interprets successful output while retaining raw reports. `web.py`, `presentation.py`, and `viewers.py` own page behavior, curated content, and bounded result parsing.

## Execution contract

`evidence_workspace.py` resolves registered evidence and complete material outputs by case-scoped IDs. Bounded signature checks, native capabilities and persisted results determine contextual actions; raw block provenance overrides apparent document headers. `evidence_web.py` exposes the optional `/evidence` workspace alongside the existing tool pages. Both interfaces submit through `compile_plan` and the same worker. A supplied `workspace_input` must match the selected case and source, and partition-map continuations must match a hash-verified allocated row. Analyst type corrections are stored with their basis; workspace progress is projected from runs rather than duplicated in a workflow-state table. Supporting reports remain accessible with their producing runs.

A `ToolAdapter` declares accepted parameter names and source kinds and implements `build()`. It returns a `Plan` containing argument lists, output redirections, deadlines, expected files, configuration snapshots, optional input segments and auxiliary files, and a named postprocessor. An optional `validate_execution()` hook rechecks installed capabilities after queue waiting; postprocessors may request execution on failed runs to summarize partial outcomes. Register a new adapter in `ADAPTERS`, add its parameter controls and payload builder, and test it through `Worker`. The disk and examination pages share catalog-driven form rendering. Avoid independent command construction in the frontend or new subprocess runners in route handlers.

Unknown parameters are rejected, so a misspelled option cannot silently fall back to a default. Clients cannot submit shell commands. The worker uses `shell=False`, closed stdin, a stable C locale, and a new process group for each step. Standard output destined for a result file stays separate from diagnostics. All workflow requests use `source_path`; there is no alternate image-path request field. Streaming pipe reads bound memory consumption; failures retain diagnostic tails and partial output. A zero exit code without required output is a failure.

`terminal.py` presents native CLI examples from validated selections, separately from worker orchestration. Preview and submission expose `terminal_command`, `terminal_ready` and `terminal_note`; unfilled evidence paths never produce a copyable placeholder. The presenter retains native arguments, writes absolute evidence paths directly into them, quotes literal paths, uses simple report names in the analyst's current directory and includes only necessary tool preparation. It does not set shell variables, export an environment or wrap commands in a generated execution script. It references installed Zimmerman resources, supplies Scalpel rules, demonstrates `file`/`find` identification and teaches native `sqlite3` inspection and SQL exports. It does not embed app executors, validators, timeout wrappers or audit manifests. The worker retains its managed execution plans and provenance independently. The shared frontend owns rendering, complete copying and script downloads. [CLI example validation](terminal-validation.md) covers native execution and browser controls.

The worker hashes input evidence before execution and verifies its recorded identity after execution. Directory membership and file identities are snapshotted when enqueued and revalidated before execution. Membership snapshots include all descendants, including those a nonrecursive identification run may not process. Directory evidence must contain regular files and directories only. Hashing large inputs costs time and falls within the execution deadline.

Segmented disk images snapshot the entire ordered sequence and hash each segment. Successful published artifacts can be reused under the same case, including from output roots; they carry a producer reference and manifest hash in `run_inputs`. Incomplete artifacts are not selectable derived inputs. Follow-up disk actions retain a context run and reject geometry changes. Text and binary sample limits are persisted per step and enforced by the shared streaming executor. Exceeding a limit produces an incomplete failed result, never a successful truncated extraction.

Partition and filesystem listings retain raw output and stream recognized records into CSV; unmatched lines remain in `unparsed.txt`. Parser CSV exports are checked for consistent rows and the required Event Log/MFT columns, then exposed through the existing pagination cache. `blkcalc -d` is verified with an explicit `blkls -l -A` step to derive a zero-based stream position across tool index-base differences. Both reports and executed arguments are retained.

`file_triage.py` builds `inventory.sqlite3` from each successful `fls` listing inside the worker's managed output directory. This index is published and hashed with the raw transcript and CSV. Triage verifies the manifest digest, keeps the verified file descriptor open, and queries SQLite in read-only immutable mode with parameterized filters and 100-row pages. Names remain filesystem observations rather than content classifications. Guided metadata/extraction plans carry an inventory entry ID; enqueue and execution both validate its metadata address, geometry, name and recovery flag. The primary input record retains the selected entry for provenance. Preparation cards project existing successful runs; no additional workflow status table, database migration, automatic scan or alternative execution path is introduced. [File triage](file-triage.md) covers UI continuity and native verification.

## Persistence and recovery

`storage.py` owns transactions and the versioned schema (`PRAGMA user_version`). Schema version 1 creates a fresh database; future schema changes must add explicit migrations. A newer database version is rejected. SQLite runs in WAL mode with foreign keys and short-lived connections. Case mutations serialize, claims are atomic, output destinations are unique, and terminal state plus manifest plus completion event commit together.

One worker per database is enforced by a Linux file lock. It renews a heartbeat while running. HTTP processes may be restarted or multiplied independently. Jobs waiting in SQLite remain queued. At startup, the worker marks formerly running jobs interrupted, kills a recorded orphan process group only when its Linux process start identity matches, and indexes any staged or already-published results. Recovery does not automatically rerun tools.

Attempts live beside their destination under `.sifted-staging/<run_id>`, keeping publication on the same filesystem. Successful and failed results are hashed and published by directory rename. Logs are saved beside the destination as `<output_path>.log`. A crash between rename and database commit is recovered by reindexing the destination. If publication cannot finish, the workspace path is recorded and preserved for inspection. Retry creates a new job and output directory; it never overwrites the old attempt.

Back up the durable database using SQLite's backup API or a tool that understands WAL. Copying only the main database while services write may omit committed changes. Preserve the output directories and adjacent logs with the database. The `.tables.sqlite3` cache can be discarded and rebuilt.

## Resource and deployment boundaries

The worker is serial by design. Subprocess output is capped while streaming, and attempt disk use is checked periodically; this is a monitored budget, not a filesystem quota. Tools can write between checks. Artifact hashing and publication follow execution and can extend elapsed time beyond the execution deadline. Process groups are terminated on cancellation, shutdown, timeout, and step completion. An interrupted attempt retains its partial artifacts and does not represent complete forensic results.

Run SIFTed with an account permitted to read evidence and create output directories. Keep database, lock, and output storage on local filesystems. `./sifted setup` installs runtime dependencies into the checkout's `.venv`; `./sifted` supervises Gunicorn and a separate job worker under the same environment. Gunicorn's HTTP processes never execute forensic jobs. Each service has its own process group, and shutdown signals both groups before waiting. If either service exits, the launcher tears down the other and returns a failure status. This also applies to startup failures and an abruptly killed Gunicorn master with surviving HTTP children. There is no authentication or multi-user isolation layer; localhost is the default binding, and `--lan` explicitly enables network access.

## Validation boundaries

`test_app.py` checks the HTTP contract and case workflows. `test_runtime.py` exercises real subprocesses using deterministic fake forensic tools, transaction races, worker process ownership, restart recovery, and manifest hashes. `test_integrated_tools.py` covers the added tool families, derived-input integrity, segment changes, and export validation. `test_launcher.py` exercises the executable through a symlink from another directory, CLI validation, Ctrl+C/SIGTERM shutdown, service death, and partial-start cleanup. `test_live_tools.py` and `test_live_disk_tools.py` run installed forensic tools through the same queue and worker using synthetic inputs. `test_volatility.py` checks typed plugin requests, installation changes, auxiliary inputs, partial outcomes and complete tree viewing; `test_live_volatility.py` checks installed discovery and real-memory analysis as described in [Volatility validation](volatility-validation.md). `test_zimmerman.py` and `test_sqlite_maps.py` check parser contracts, verified captures, replay membership, frozen profiles, read-only queries, WAL and blob evidence; `test_live_zimmerman.py` verifies all eleven workflows with native SIFT tools and known upstream artifacts, as described in [Zimmerman validation](zimmerman-validation.md). `test_browser.py` optionally checks Chromium rendering, previews, submission, completion with the event stream unavailable, and listing-to-extraction-to-examination navigation.

The live smoke suite establishes CLI integration for the installed workstation and synthetic inputs. It does not establish parser accuracy across forensic artifact versions. Adding a parser option requires a meaningful adapter/worker test and, when feasible, a small documented fixture with known expected results.

`test_evidence_workspace.py` checks case-scoped selection, content suitability, all eleven Zimmerman actions, retained block identity, material-output filtering, result reuse and tampered partition maps. Chromium checks follow the optional workspace through disk extraction and SQLite parsing, including shared form prefilling and mobile layout. `test_live_evidence_workspace.py` runs the native partition-to-PDF journey with 512- and 4,096-byte disk sectors and a Volatility process listing against the digest-pinned public Windows sample.

### Carving contract

The dedicated `carving.py` adapter uses the same plans, queue, worker, budgets, process groups, staging, provenance and publication as every other workflow. It owns raw-stream input validation and faithful Scalpel 1.60 profile snapshots; no carving subprocess runs in an HTTP route. Shared result postprocessing dispatches to a streaming validator that reconciles native audits with captured files and compares each recovery to its source range before publishing the recovery CSV. Native rounded Foremost sizes and audit record numbers are never treated as exact lengths or offsets. The worker rechecks input identities after result validation as well as after tool execution, covering interpretation of derived results. Carving analysis uses the existing paged CSV viewer and derived-artifact baseline checks; it adds no independent persistence or execution layer. The two carving pages use one frontend controller and backend-provided canonical selections.

[Carving validation](carving-validation.md) describes the fixture generation, live workstation checks and native limits.

Output paths must be representable as UTF-8 for the database and web interface. If a tool generates an invalid filename, publication fails before the staging rename; the attempt is retained intact, the durable run ends in error, and the worker can continue. Raw filename bytes are preserved in the retained workspace rather than renamed or silently dropped.

### Managed input captures and configuration

Adapters can declare `Plan.input_copies` for inputs that native tools may replay or otherwise modify. The worker only copies members already verified against their registered evidence hashes, verifies each streamed copy, and stores them beneath the private input directory. Original sources and sidecars remain covered by post-execution checks. Generated configuration supports safe nested paths, is frozen in the persisted plan, and is retained under `_sifted/` with its directory structure. Publication rejects changed configuration, symlink redirects or occupied provenance destinations and preserves the failed attempt. Private evidence copies are not published as duplicate result artifacts. Optional per-step stderr captures remain inside managed output and share the ordinary streaming log, process lifecycle and budgets.
